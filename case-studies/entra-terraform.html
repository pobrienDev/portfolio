Moving an Entra ID identity layer from portal clicks to Terraform

Two of my Graph API automation tools started with the same hand-built setup: register an app, add permissions, grant consent, create a secret, paste it into a .env. I replaced that with versioned, reviewable code, then let it grow into the identity foundation for two more repos.

The problem

My provisioning and stale-accounts CLIs both authenticate to Microsoft Graph as an app registration. Creating that registration was a checklist of portal clicks that nobody could review, diff or reproduce, and the resulting client secret lived in a local file. It was also the one layer of my portfolio with no infrastructure-as-code in it, and that shows up in nearly every cloud and identity job posting.

The goal was narrow on purpose: provision exactly the identity infrastructure those tools depend on, as Terraform, applied against a real tenant, with the one concept interviewers probe on most (state versus reality) demonstrated rather than described.

Constraints

  • A personal tenant only. Everything runs in my own Entra ID tenant and an Azure free-tier subscription, never an employer's.
  • Public from the start. The repo is a portfolio piece, so it has to be public, which means no tenant, subscription, client or object IDs, no tenant domain, and no resource names that encode any of those, anywhere in the history or in CI logs.
  • Five resources, no more. The plan fixed scope at a resource group, an app registration with permissions, a service principal with consent, a Key Vault for the secret, and remote state. If a sixth looked tempting, that was the signal to write the README instead.

Decisions worth defending

Permissions came from the code that uses them, not from a guess. I read both tools' Graph calls and granted the four application permissions they need. The two that let an app reset passwords and remove MFA methods are behind a flag that defaults to off: a leaked secret with those can take over any account in the tenant, so they should be a decision, not a default.

Key Vault keeps the secret out of code, not out of state. Terraform generates the secret, so the value is recorded in state in plaintext. That is unavoidable with this approach, and I say so in the README rather than claiming otherwise. It is also the real justification for the next decision.

State storage is locked down like the credential store it is. Account keys disabled so access is Entra ID only, no anonymous blob access, TLS 1.2 minimum, a data-plane role scoped to one container, blob versioning and soft delete for recovery, and its own resource group so terraform destroy on the workload can never delete the state it is using.

Nothing identifying is committed. Tenant and subscription IDs come from a gitignored variables file; the state storage account name is passed at init time from a gitignored partial backend config. Graph permission IDs are looked up by name at plan time, so the config reads "User.ReadWrite.All" instead of an opaque GUID, and no GUID ever needs to be committed.

The owner is an explicit input. Early on, each resource's owner was "whoever is running Terraform". That is me on my laptop and the CI identity in Actions, which meant the same code and the same state produced different plans depending on who ran it. Infrastructure code should not mean different things to different callers. This one I would not have found without a second identity running the same configuration.

State versus reality

After the first apply I deleted the resource group by hand in the portal and ran a plan with no code changes. Terraform has no memory of what it did; every plan is a three-way comparison between what the code declares, what state believes exists, and what Azure actually reports. The refresh caught the gap and the plan proposed closing it, touching only the one resource that drifted.

CI with no stored secret, and the three fixes it took

The workflow authenticates with OIDC workload identity federation. GitHub mints a short-lived token for each run, and a federated credential on a dedicated CI app registration tells Entra ID to trust tokens from this repository. The CI identity holds only read roles, and plans with -lock=false so it never needs to write a lease. It can plan; it cannot apply. Because the repository is public, so are its logs, so raw plan output goes to a file and only a redacted copy is ever printed or posted to the pull request.

Getting to the first green run took three fixes, each more instructive than the last.

1. The subject claim did not match

I had written the credential's subject as repo:owner/name:ref:refs/heads/main. GitHub's newer immutable subject format embeds numeric owner and repository IDs, and the match must be exact. I changed the credential to the immutable format rather than switching the feature off: a repository name can be re-registered by someone else after a rename or deletion and would inherit the cloud trust, while an ID cannot be.

2. Least privilege, one level too narrow

The next run signed in, then failed with a 403 reading the storage account. I had scoped the CI identity's Reader role to the state container, but a data source in the configuration reads the storage account. The fix moved one role assignment up one scope: still read-only, and with account keys disabled there is nothing at account level that unlocks the data.

3. CI's plan disagreed with mine

Same code, same state: locally "No changes", in CI "4 to change, 1 to replace". This was the implicit-owner problem described above, and it became the explicit admin_object_id input. It is also the strongest argument I have for running CI on infrastructure repositories even when a laptop apply would do: a second identity exercising the same configuration finds a class of bug that one person running it never will.

From a project to a foundation

Once the pattern existed, two sibling projects needed pipeline identities of their own: a daily credential monitor that scans the tenant for expiring secrets, and Conditional Access policies as code, which needs a read-only identity for plans and drift checks and a separate write identity reachable only from an approval-gated GitHub environment. App-only identities are not subject to Conditional Access, so the one permission that can rewrite the tenant's front door had to be unreachable without a human approving a deployment.

Those arrived as two more hand-written files, the same pattern written three different ways. A cleanup pass consolidated all four identities into one table: display name, which repository is trusted, which workflow contexts, which Graph permissions, which Azure roles. One set of for_each resources turns each row into an app registration, service principal, federated credentials, consent grants and role assignments. Adding an identity is now adding a row.

The refactor renamed every one of those resources in state, and three repositories' secrets depend on their client IDs, so recreating them was not an option. Terraform moved blocks recorded all thirty address changes; the plan, locally and in CI, showed thirty moves, zero to add and zero to destroy before anything was merged. The configuration shrank from 669 to 578 lines and from 19 input variables to 9, and the only runtime change was three description strings.

Outcomes

  • Every resource applied against a real tenant, with the drift exercise and apply output in the README as evidence.
  • Pull requests get a redacted plan comment within about a minute, from an identity that holds no write roles and no secret.
  • Three audits of the public surface (every commit, every workflow log, pull request text and repository metadata) found zero tenant identifiers. The only GUIDs in CI logs were GitHub's own runner temp-file names and Microsoft trace IDs.
  • The repo is now the identity layer that two other public projects authenticate through.

What I would do differently in production

  • Purge protection on, longer soft-delete retention, and private endpoints for Key Vault and the state storage account.
  • A certificate or a managed identity instead of a client secret for the automation app, which would keep the credential out of state entirely.
  • A separate apply pipeline with a protected environment and required reviewers, rather than applying from a laptop.
  • Split state per environment once there is more than one.
