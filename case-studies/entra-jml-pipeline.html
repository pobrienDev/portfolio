Case study · Identity lifecycle automation

Account lifecycle driven by the HR record, with nothing to run and no credentials to store

My onboarding CLI cut account setup from 20 or 30 minutes to one or two, but somebody still has to run it, it authenticates with a client secret, and it has no answer for a person who changes teams. I rebuilt it as a service. An HR export lands in storage, and Azure Functions create, update or offboard the Microsoft Entra ID accounts to match, as a managed identity, in my own sandbox tenant with made-up employees.

The problem

Account lifecycle done by hand fails in three different ways. A new hire waits on day one. Someone who changed teams keeps the access they no longer need, because nobody thinks to remove it. Someone who left stays signed in until a person remembers to act. My provisioning CLI fixed the speed of the first and the last, but it is still a command a person runs, it has no mover step at all, and behind it sits a client secret with tenant-wide write access.

The goal was to take the person out of the loop without taking the judgement out: the same Graph logic, triggered by the HR record instead of by me, with nothing stored that could leak, and built so that running any part of it twice is harmless.

How it works

Every resource in the picture is defined in Terraform. Neither function holds a key to anything: storage, the queue, the table, telemetry and Graph are all reached as the same managed identity.

EventIn the HR exportWhat the pipeline does
JoinAn employee ID appearsCreates the account with a collision-safe UPN, sets department, title and hire date, adds the department’s groups, sets the manager
MoveDepartment, title or manager changesUpdates the attributes, adds the new role’s groups and then removes the old ones, updates the manager
LeaveSomeone drops off the feed or is marked terminatedDisables sign-in and revokes sessions first, then removes the managed groups and direct licenses, then stamps the leave date

Run it twice, nothing changes

That is the property the design is built around, and it holds at two levels. The parser queues only what differs from the last export, so a repeat upload queues nothing. And if a message is delivered twice anyway, every step in the processor reads the directory first and acts only on the difference.

Decisions worth defending

A queue between the two functions, and no retry logic in mine. One export can mean hundreds of changes, each of them several Graph calls that can be throttled or fail on their own. With one message per person, a failure belongs to that person alone. The processor contains no retry loops and swallows no errors: it raises, the queue retries the message five times, then sets it aside in a poison queue where it is visible and nothing is lost, while everyone else’s changes go through.

No secret anywhere, including the places secrets usually hide. Azure issues the Function app its tokens at runtime, so there is no client secret. The storage account has account keys disabled, so there is no connection string either. Application Insights accepts telemetry only from Entra ID-authenticated callers. Nothing in the code, the configuration, the Terraform state or the repository would be worth stealing.

Two identities, because deploying code and changing the directory are different powers. The identity the pipeline runs as can create and disable accounts across the tenant. The one GitHub Actions deploys as can push code to a single Function app and nothing else: no Graph permissions, no storage access, no rights over the infrastructure. Its federated credential trusts only the repository’s approval-gated environment, so a job that skips the approval cannot get a token. Terraform is applied by a person.

People are matched on the HR system’s ID, never on name. Names change and collide; the employee ID does not. A name change in HR does not create a second account, and two people called J. Lee do not fight over one.

A diff against a snapshot, because a file cannot say who is missing from it. The pipeline has to know who left. Comparing each export with the last one turns “no longer listed” into an event. It also means a row rejected for a typo is carried forward as last known, so a mistake in one row never reads as that person resigning.

A brake on mass change. A truncated export looks, to a diff, exactly like most of the company leaving. If one file would offboard more than ten percent of the people the pipeline knows, nothing in it is processed, the snapshot is left alone, and a person decides.

It removes only what it granted. The mover and the leaver take a membership away only if the department map names the group. Anything else on an account was put there by someone for a reason the pipeline cannot see. Those memberships, and any directory roles, are recorded as follow-ups for a person.

Lock out first, clean up second. The order comes straight from the CLI. A leaver is disabled and has their sessions revoked before anything else happens, and if the disable fails nothing further is attempted. The leave date is stamped last, only when every step before it worked, which is also how a repeat run knows the job is finished.

What deploying found that tests could not

Every change went through a pull request. For the two stages that could only be proven in Azure, the branch was deployed to the sandbox and tested end to end before it was reviewed. Four things came out of running it for real that no unit test would have shown.

The standard Terraform resources assume account keys, twice. The table resource makes a key-only call on every refresh, so it failed with a 403 on a storage account with keys disabled. The Function app resource went further: in managed-identity mode it writes a storage connection string with an empty key into the app’s settings. That setting takes precedence over the identity-based ones, so the host failed every start against its own storage. The app had sat empty since the first stage, so it only showed when code was deployed to it. Both resources are now created through the Azure management API, and a moved block made the second an in-place update instead of a rebuild.

A permission that had not taken effect yet. Stamping the leave date needed one more Graph permission. It was granted two minutes before the first offboarding ran, and both leavers’ final step was refused. By then both had been locked out and removed from their groups. The queue retried, each retry skipped what was already done, and the third attempt stamped the date. Nobody intervened. It is the cleanest demonstration of the design I could have asked for, and it was not planned.

Two people offered the same address. The first dry run against the tenant offered jlee@ to both Jordan Lee and Jamie Lee, because in a dry run the first account does not exist when the second is checked. A real run has the same hole for a few seconds after each create. Addresses handed out earlier in a run now count as taken, and a retry that finds its own account behind a “taken” address recognises it instead of creating a second one.

A dry run that used up what it saw. The parser saved the snapshot in dry-run mode, so uploading the same file after switching dry run off would have produced nothing. That one was caught by reading the code before dry run was tested, not by a failure.

Outcomes

  • Uploading a CSV creates accounts with no manual step. Event Grid called the parser six seconds after the upload, and the deployed pipeline has since created, moved and offboarded accounts in the sandbox, with each change read back through Graph to check.
  • The plan’s three failure scenarios were run for real, not only in tests. A malformed row was rejected without touching that person. A nonexistent manager failed five times, was audited and moved to the poison queue, and the alert fired. A file with half the company missing was refused, and every account was still enabled afterwards.
  • Six pull requests, each reviewed before merging, and CI now gates every merge. The deploy workflow signs in through OIDC as an identity that can do exactly one thing, and waits for an approval before it does it.
  • The managed identity needed four Graph permissions, and one I had expected to need turned out to be unnecessary. It holds nothing it does not use.

What I would do differently in production

  • Read from the HR system’s API or Entra’s inbound provisioning API instead of a CSV drop. The file is a stand-in for a feed.
  • Issue a Temporary Access Pass to each new hire. Today a new account gets a random password that nobody is shown, which is safe and not yet useful.
  • Decide what a rehire means. A returning leaver’s disabled account is deliberately left alone, which is the cautious answer and not a complete one.
  • Put the storage account and the Function app behind private endpoints, and have a second person approve any change to the department map, since that file decides who gets what access.
  • Tighten the alert. It evaluates every fifteen minutes, which is fine for a sandbox and slow for a failed offboarding.
