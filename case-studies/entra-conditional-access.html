Case study · Policy as code

Conditional Access policies that change through a reviewed pull request

Conditional Access is the front door of a Microsoft Entra tenant, and it is normally edited by hand in a portal where one wrong checkbox can lock out every administrator. I built a seven-policy baseline in Terraform and built the pipeline around it so that a dangerous change cannot merge, a merged change cannot apply without a human, and a portal edit cannot go unnoticed.

The problem

Every Entra tenant I have worked in manages Conditional Access the same way: an administrator opens the portal, edits a policy, and clicks save. There is no diff, no second pair of eyes, no record of why, and no way to know a week later that someone loosened a policy. The failure mode is not hypothetical. A policy that targets all users and all apps with a block, or one that forgets to exclude the emergency accounts, locks the people who could fix it out of the tenant.

The goal was to make Conditional Access behave like any other reviewed code: every change is a pull request with a plan, the dangerous shapes are caught by a machine before a human has to spot them, applying needs an explicit approval, and drift from the portal is detected daily. It runs in my own sandbox tenant, and it builds on the identity and state layer from my Terraform case study.

The baseline

Seven policies, named CA###-Who-What-Control so they sort predictably and can be referenced unambiguously. Every one excludes the break-glass group, and every one was created in report-only.

PolicyApplies toControl
CA001All users, all appsRequire MFA
CA002Five privileged directory rolesPhishing-resistant authentication strength
CA003Legacy authentication clientsBlock
CA004Azure management: portal, CLI, PowerShellRequire MFA
CA005Sign-in risk medium or highMFA, re-prompted every sign-in
CA006User risk highMFA and password change, every sign-in
CA007Registering security info outside trusted locationsRequire MFA

Two of those overlap on purpose. CA004 looks redundant next to CA001, since Azure management is one of "all apps", but if someone later adds an exclusion to CA001 the management plane stays protected. CA003 exists because legacy protocols cannot do MFA at all, so CA001 never applies to them; only a block stops them.

Decisions worth defending

Terraform reads the break-glass group; it never owns it. The two emergency accounts and their group were created by hand, and the configuration only looks the group up. A bad apply can therefore never delete it or change who is in it. The lookup also carries two postconditions: if the group has fewer than two members, or is not the group its name says it is, Terraform refuses to plan anything. An exclusion group with no members excludes nobody, and every policy would then apply to the emergency accounts too.

The safety rules are code, not memory. CI converts the plan to JSON and a Python script inspects every Conditional Access policy in it. The desired-state rules run against every policy in the plan, not just the ones changing, so a policy that drifted in the portal and was then adopted into code still fails. The script fails closed: a value Terraform cannot know until apply time counts as wrong. And the break-glass group's ID comes from CI configuration, never from the repository, so a pull request cannot redefine which group must be excluded.

Two identities, because app-only identities are not subject to Conditional Access. That is the uncomfortable fact underneath this whole design: an identity holding Policy.ReadWrite.ConditionalAccess could rewrite every policy in the tenant and no policy could stop it. So the write permission lives on a separate app registration whose federated credential trusts only the repository’s approval-gated GitHub environment, named production although the tenant it deploys to is my personal sandbox. A job that skips the environment gets a different token subject and cannot obtain a token for the write identity at all. Neither identity has a client secret; both authenticate through GitHub OIDC federation.

Report-only first, enforce one at a time. New policies are created in report-only, and a guardrail refuses to create one enabled. Switching a policy to enforced is its own reviewed pull request, taken after validating against sign-in logs and What If, one policy at a time. The whole baseline is deployed; enforcement is the next phase.

Deleting a policy is a deliberate act. Removing, replacing or disabling a policy fails CI unless ALLOW_CA_DELETE is set, which no workflow currently does; a removal needs a deliberate workflow change as well as a reviewed PR. Protection should not disappear because a file was deleted in passing.

The guardrails

RuleWhat it prevents
Break-glass excludedA policy that could lock out every admin, including the emergency accounts

No silent removalDeleting, replacing or disabling a policy without an explicit, reviewed decision
No all-users, all-apps blockThe classic self-lockout. CA003 passes because it targets only legacy clients
Risk policies re-promptAn existing session carrying a risky sign-in through unchallenged

The checks are about two hundred lines of standard-library Python with tests that build small plans in the real terraform show -json shape, plus one redacted plan captured from the tenant, so the fixtures match the shape Terraform really emits. The same rules could be written in Rego and run with Conftest, which is the more common tool; Python keeps them in the stack the rest of my projects use, with no extra binary in CI.

The pipeline

WorkflowIdentityWhat happens
planca-plan (read)On every pull request: guardrail tests, format, validate, plan, guardrails on the plan JSON, then a redacted plan and verdict posted to the PR. main requires both checks to pass before merging.
applyca-plan, then ca-apply (write)On merge: a read-only preview, then the production GitHub environment waits for a human. After approval the write identity re-plans, re-runs the guardrails, and applies only that saved plan.
driftca-planDaily: a plan with a detailed exit code. Drift opens or updates one issue with a redacted diff; no drift closes it.

All four plans run through one composite action, so there is a single definition of how the repository initialises and plans. The logs are public, so every line of Terraform output passes through a redaction script, which masks GUIDs, tenant domains, storage names and IP ranges and has its own tests. The plan JSON never leaves the runner.

The bug that made the safety net decorative

In a cleanup pass about two weeks after the first version shipped, I found that the guardrail step had never been able to fail a pull request. The step piped the script's output through tee so it would show in the log, and GitHub's default shell for run steps does not set pipefail. The step's exit status was tee's, which is always zero. Every guardrail check had been green, including the ones that should not have been.

The fix captured the script's exit code explicitly. The more important fix was proving it: a throwaway pull request that strips CA004's break-glass exclusion, which must go red and must say Guardrails: FAILED in its comment. It does. The pull request was closed without merging and stays in the history as the record that the net catches. A safety control that has never been seen to fail has not been tested.

Outcomes

  • The full seven-policy baseline is deployed to a real tenant in report-only, every policy excluding the break-glass group, with the exclusion enforced by a machine rather than a checklist.
  • Every policy change has gone through a pull request; since the pipeline landed, every one has carried a redacted plan and a guardrail verdict. Eleven PRs landed in the first day; the cleanup that found the tee bug was the twelfth.
  • The daily drift check has run green every day since it was enabled. It has not had to open an issue yet, which is the point: the day it does, the diff is already redacted and waiting.
  • The write permission for the tenant's front door is reachable from exactly one place, and that place requires a named human to click approve.

What comes next, and what I would do differently in production

  • Enforce the policies one at a time, validating each against sign-in logs and What If before switching it from report-only.
  • Require two reviewers on the GitHub environment rather than one, and a second approver for any pull request that touches an enforced policy.
  • Add Entra's own protections alongside the pipeline: a policy that requires phishing-resistant MFA for the Conditional Access Administrator role, and alerting on any policy change not made by the apply identity.
  • Exercise the break-glass accounts on a schedule, so the emergency path is known to work before it is needed.
