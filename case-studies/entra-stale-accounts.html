A stale-account check that any Entra admin can pip install

While automating provisioning I kept needing the same question answered: which accounts have not signed in for ninety days, and which of those never signed in at all? The answer became a small, read-only command-line tool, published on PyPI, that works against any tenant and never changes anything.

The problem

Accounts that nobody uses are a quiet risk: they keep a working login and often a paid license, and nobody is watching them. The Entra admin center can show last sign-in per user, but not as a list filtered by threshold, exported for a manager, or run on a schedule. Every time I needed that list I was writing the same loop over the Graph user collection by hand.

The tool does one thing. entra-stale-accounts check --days 90 prints a table of enabled accounts with no sign-in in ninety days, with accounts that have never signed in always included and sorted to the top, since no activity at all is at least as noteworthy as an old sign-in. --output csv turns it into a file to hand to someone; --licenses adds a column of each account's license SKUs, which turns a stale list into a reclaim list.

Decisions worth defending

Read-only by construction, and the security policy says so. The only Graph calls are reads of the user list and, with --licenses, the tenant's SKU list, plus the token request. Nothing is ever created, modified or deleted, and the repository's SECURITY.md states that as a commitment with a private reporting channel, not as a feature. An admin evaluating a tool that wants AuditLog.Read.All on their tenant deserves to be told exactly what it will and will not do.

The logic is pure, so the tests need no mocks. Everything that parses timestamps, applies the threshold and formats output lives in one module that never touches the network or configuration. Those functions are tested directly with plain values. The Graph client is the only part that needs a fake, and the whole suite runs in milliseconds with no credentials and no tenant.

Say where the licensing wall is. The signInActivity field the tool depends on requires an Entra ID P1 or P2 license on the tenant, not just API permissions. Without it the field comes back empty and every account looks like it never signed in. The README calls this out before setup and the troubleshooting section repeats it: if every account shows never, suspect the license, not your users.

Names are user-controlled input, even in a CSV. A display name can start with = or +, and Excel will execute it as a formula when the report is opened. Exported values that start with a formula character are prefixed so they render as text. A report about a tenant's users should never trust those users to have harmless names.

Publishing has no secret either. Pushing a version tag runs the tests, builds the package, and publishes to PyPI through trusted publishing: GitHub's OIDC token is exchanged for a short-lived PyPI credential inside a dedicated environment. There is no API token to store or rotate, the same pattern I later used for Azure in the Terraform case study.

What a run looks like

Three bugs only a real tenant could find

The first release passed every test and failed against the first real tenant it met. The test suite was faithful to how I thought Graph behaved; the next three patch releases were corrections to that model, and each one is a changelog entry.

  1. Graph caps the page size at 120 when signInActivity is selected. The tool asked for pages of 999, which is the documented maximum for the user collection, and got a 400 instead. The cap is a property of that one field, and the only way to learn it is to request it.
  2. Graph emits seven fractional digits in timestamps. Python's ISO parser before 3.11 accepts exactly three or six, so on 3.9 and 3.10 affected accounts raised a parse error that was caught and reported as never signed in. That is the worst kind of bug for an audit tool: wrong, confident and plausible. Fractional seconds are now normalised before parsing, and CI runs the suite on every version from 3.9 to 3.13.
  3. A .env in the current directory was ignored after pip install. The dotenv library's default discovery searches from the package's install location, not from where the command is run. It worked from a source checkout, where those are the same place, and silently found nothing once installed. Found only by running the published package rather than the repository.

The lesson I took from these is to treat the published artifact as a different thing from the source tree, and to run it, installed, against a real tenant before calling a release done. That is now the last step before every tag.

Outcomes

  • Installable with one command on any tenant; works with an app registration holding two read permissions, and degrades gracefully without the optional third.
  • Seven releases from 0.1.0 to 0.2.1 in ten days, each with a changelog entry, a git tag and a GitHub release, published automatically with no stored credential.
  • Tests run on five Python versions on every push, and the suite has never needed a credential or a network connection.
  • It became the proving ground for patterns I reused elsewhere: pure logic modules, honouring Retry-After on throttling, OIDC publishing, and treating user-controlled strings as hostile wherever they end up.

What I would do differently next

  • A --since option that reads the last report and shows only what changed, so a scheduled run produces a diff rather than a full list.
  • Signed release artifacts, so the Windows launcher is not blocked by application control policies and the workaround in the troubleshooting section is unnecessary.
  • A certificate credential option for the app registration, for admins who do not want a client secret anywhere on the machine that runs the report.
