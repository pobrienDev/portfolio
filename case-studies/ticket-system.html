A helpdesk ticket system where every change has a name on it

Help-desk work is a queue of small decisions: who owns this, how urgent is it, is it done. The tools I used day to day were good at storing tickets and bad at explaining them. I built a ticketing app whose API records who changed which field, from what, to what, and whose access rules never confirm that a ticket you cannot see exists. It is live, free-tier hosted, and deployed only from a main branch that has passed every check.

The problem

A ticket queue is shared state edited by several people at once. The questions that matter later are not "what is the status" but "who moved it to resolved, when, and what was it before". Most small ticketing apps answer the first and shrug at the second. The other common failing is access control that leaks: a user asks for a ticket that is not theirs and gets a 403, which tells them the ticket exists.

The app is a React front end over a FastAPI service with PostgreSQL behind it. Users register and sign in, open tickets with a priority and category, comment on them, and move them through an explicit lifecycle. Admins assign tickets, create categories and delete tickets. Every edit to a ticket's status, assignee, priority, title, description or category writes an audit row with the actor, the old value and the new one, and the ticket's history is one request away.

Decisions worth defending

The audit trail lives in the write path, not in a trigger or middleware. The one endpoint that edits a ticket compares each incoming field with the stored value and records a row only for the ones that changed, so re-sending the same value leaves no trace and a single request that changes three fields leaves three rows. Values are clipped to 120 characters so a rewritten description does not bloat the history. It is also honest about its edges: creating a ticket, deleting one and adding a comment are not audited, and the history is deleted with its ticket.

Out of scope means 404, not 403. A non-admin sees only tickets they own or are assigned. Asking for any other ticket returns the same not-found answer as asking for one that never existed, so the API never confirms a ticket ID is real to someone who should not know. The owner is always taken from the token, never from the request body.

The lifecycle is a map, not a free text field. Five statuses, from new to closed, with an explicit table of allowed transitions enforced in the API and mirrored in the database as an enum. A closed ticket can go nowhere but back to open, an illegal move is refused with a 409, and the client's own transition table is tested against the same map. The migration that introduced the new status also added the SLA columns, so the rule and the data arrived together.

Authentication is small on purpose, and the limits are stated. Stateless JWTs signed with HS256, sixty-minute expiry, bcrypt passwords with an 8 to 72 byte cap, and a signing secret that must be set and at least 32 bytes or the service refuses to start. Unknown emails are checked against a dummy hash so login timing does not reveal which accounts exist, and login and registration are rate limited per client IP. There is no refresh token and no revocation; a token is valid until it expires. That is the right trade for a portfolio-scale app, and the README says so instead of implying otherwise.

Two roles, and admin is a flag, not a feature. There is one boolean on the user, and the only way to set it is the seed script. No endpoint promotes a user, so an attacker who gains one account cannot talk the API into a second role. The cost is that user administration happens outside the app, which I would change before this ran for a real team.

The list endpoint filters by status, category, assignee and owner, searches title and description with the wildcard characters escaped so a search for % means a percent sign, sorts by priority, creation or due date, and pages with a limit capped at 100. Every string field has a length cap, from 200 characters for a title to 10,000 for a description, enforced in the schema before anything reaches the database.

SLA due dates by priority

Each priority maps to a response window, four hours for the most urgent down to two weeks for the least, and a ticket's due date is set from that window when it is created. Overdue is a derived state, unresolved and past due, so nothing has to run on a schedule to flag it. The first version had a bug here, described below.

Testing on two databases

The backend suite runs against in-memory SQLite locally, which keeps a full run under a minute and a half, and against a PostgreSQL 16 service in CI, which is what production uses. The CI job does more than run tests: it applies every migration, runs Alembic's own check for model drift, verifies the status enum and the priority constraint directly against the database, then downgrades to nothing and upgrades again, so a migration that cannot be reversed fails the build. A second job lints, tests and builds the front end. A third builds the Docker image and import-checks the application inside it, which catches a missing dependency but does not start the server; a pull request that boots the real container and waits for its health check is open and not yet merged.

Deployment is the last job and depends on the other three. It runs only for pushes to main, under a concurrency group so two merges cannot race, and it calls the host's deploy hook with the exact commit it just tested. The host's own auto-deploy is off, so there is exactly one way code reaches production: through a green pipeline.

Three fixes worth telling

An escalated ticket kept its old deadline

The due date was computed once, at creation. Raise a ticket from priority 3 to priority 1 and it kept its three-day deadline instead of the four-hour one, which defeats the point of escalating. The fix recomputes the due date from the ticket's creation time using the new priority, so an escalation can make a ticket immediately overdue; that is the correct outcome, since the clock started when the ticket was opened. Four tests cover it: priority changes recompute, the change is visible to the next reader, editing other fields leaves the date alone, and re-sending the same priority leaves it alone. The pull request records that the tests were written first and three of them failed against the old code.

A free tier that sleeps

The API runs on a free tier that spins down when idle, and a cold start can take half a minute. The first version of the front end showed that as an error. The fix made the client honest about it: a fifteen-second timeout on each request, up to eight retries ten seconds apart while the service wakes, a warm-up ping to the health endpoint the moment the page loads, and a message on the login page that says the server is waking and which attempt this is. Eleven tests pin the retry behaviour. The portfolio card says the same thing the app does: the first request can take a minute.

Sixteen audit items in one pull request

Two months after the first commit I audited the whole repository and fixed the sixteen clear-cut findings together. Some were correctness: the seed script accepted a blank admin password; the ticket update did not lock the row, so two concurrent edits could interleave; search did not escape SQL wildcards. Some were operational: the container now execs the server so it runs as PID 1 and receives signals, the deploy hook passes the commit SHA, the enum is dropped on downgrade so the migration really is reversible, and development dependencies are split from runtime ones. The test count went from 176 to 192 in that change.

Outcomes

  • A ticket's full history, who changed what and when, is a single request, and the rule that produces it has one owner in the code.
  • Access control that cannot be probed: outside your scope, every ticket ID looks the same.
  • 192 backend tests at 96% coverage and 141 frontend tests, run on every push and pull request, with a Postgres-backed migration round trip in CI.
  • Live on free-tier hosting with a client that handles the cold start, and a deploy path that only starts from green main.

What I would do differently next

  • Refresh tokens with server-side revocation, and the access token out of local storage. The current design is stated honestly, but it is the first thing I would change for a real team.
  • Audit ticket creation, deletion and comments, so the history starts at the beginning.
  • Boot the container in CI and wait for its health check, which the open pull request already does.
  • User administration endpoints, so promoting an admin does not mean running a script against the database.
  • Shared storage for the rate limiter, so limits hold across more than one API process.
