A Medicaid enrollment pipeline that can run twice and change nothing

Everything else on this site is identity automation or a web app. This is the piece that was missing: a small data pipeline, built end to end on real public health data. Every week it pulls state Medicaid and CHIP enrollment from a CMS API, validates it, and upserts it into PostgreSQL, and it is built so that a rerun, a bad batch, or a crash halfway through cannot leave the table wrong.

The problem

CMS publishes monthly Medicaid and CHIP enrollment for every state and the District of Columbia as open data, back to September 2013. It is a good stand-in for the recurring data pull most teams have somewhere: a source that someone downloads by hand, tidies in a spreadsheet, and pastes into the place people actually query.

Doing that by hand has three predictable failures. The same month gets loaded twice. A malformed file gets loaded anyway. Or the job stops partway and nobody can say afterwards what state the table is in. The pipeline is a single command, python -m pipeline.run, and each of its design decisions exists to rule out one of those.

Decisions worth defending

Validate before anything is written. The transform is a pure function: a DataFrame in, a DataFrame out, no I/O. Its output goes through a validation gate that rejects an empty batch, unparseable dates, state codes that are not two capital letters, negative counts, and duplicate keys, and reports every problem at once rather than the first. Only data that passes reaches the database. The table's own CHECK constraints and primary key are a second line of defense, not the first.

One transaction, staging then upsert. The cleaned rows are written to a staging table and merged into the real one with INSERT … ON CONFLICT (state_code, report_month) DO UPDATE, and both steps share a transaction. A crash leaves nothing half-written, and a second run finds every key already present and updates it in place. One of the integration tests proves the rollback: a batch that violates a constraint leaves the previously loaded rows exactly as they were.

The updated report wins, by rule and not by row order. Most state-months appear in the source twice, once as a preliminary report and once as an updated one, often with different totals. The transform reads the source's own final-report flag and keeps the updated row, so the result does not depend on the order the API happens to return rows in. The newest month has only a preliminary figure, and that is kept as it is.

Every run leaves a row, including the ones that fail. Before extracting anything the run inserts a row into pipeline_runs with status running. When it ends, that row gets the finish time, the status, how many rows were extracted and loaded, and the error if there was one. The process then exits non-zero on failure, so the scheduler shows a red run and the question “did last week's load work?” is a SQL query.

Tests may only empty a database whose name ends in _test. The integration tests truncate the tables they use. They connect with a separate URL and skip, with the reason printed, if the database name does not end in _test. Running the suite on a machine that also holds loaded data cannot wipe it.

Keep what arrived. Each extract is saved untouched before it is transformed. When a run fails validation, the evidence is a file on disk rather than a response that no longer exists.

What a run looks like

Three consecutive runs against a local database, two through the API and one through the CSV fallback, each recorded in the audit table. The enrollment table held 5,661 rows after the first and after the third.

Three things the plan got wrong

The project started from a written plan with a schema, module outlines and a test list. Three of its assumptions did not survive the real dataset and the real tooling, and each one changed the code.

  1. It assumed one row per state and month. In the release it was built against, 5,559 of 5,661 state-months had two rows, preliminary and updated, and the totals differed in 3,485 of them. The plan's drop_duplicates(keep="last") would have produced the right answer only because the API happens to list the preliminary row first. The transform now chooses on the final-report flag, and a test feeds it both orders.
  2. It assumed the CSV fallback had a stable address. The catalog's download link is named for the month's release, so it changes every month and a hard-coded fallback would have gone stale with the next release. The datastore API serves the same rows as CSV from a fixed endpoint, and the fallback uses that, through the same retrying session as the API path.
  3. It let the tests share the database. The planned test fixture truncated the tables at whatever DATABASE_URL pointed to. Locally the only database was the one real runs load into, so running the integration tests there would have emptied it. That is where the _test rule above came from.

A smaller one in the same spirit: an unset repository secret reaches a workflow as an empty string, not as a missing variable, so the configuration check rejects blank values as well as absent ones. Otherwise the first sign of a missing secret is a confusing connection error.

How it was built

This project was built with an AI coding assistant, Claude Code, working from that written plan, in about a day. The assistant wrote most of the module and test code and ran the checks against the live API. I directed the build and set up the hosted database, the repository secrets and the schedule. I am stating that plainly so a reader knows how this one was made.

Outcomes

  • One command extracts, validates and loads the full history: 51 jurisdictions, September 2013 to July 2026 as of the October 2026 release, in a few seconds.
  • Rerunning is safe by construction, and shown rather than claimed: three consecutive runs through two different source paths left the same 5,661 rows.
  • 49 tests at 98% coverage. The unit tests need no network or database; the integration tests run the load and the whole orchestrator against a real PostgreSQL 16 service on every push.
  • A weekly scheduled workflow loads into a hosted Postgres, with a concurrency guard so two loads cannot overlap. Its first run loaded 5,661 rows and recorded itself as run 1.

What I would do differently next

  • Store whether each figure is preliminary or final. The table keeps the best available number for each month but does not say which kind it is, and an analyst comparing recent months should be able to tell.
  • Reload a rolling window of recent months instead of the full history. “Only new months” would be wrong for this source, because earlier months are revised when preliminary figures become final.
  • Send failures somewhere a person will see them. A failed scheduled run currently produces a red mark and a GitHub email; a Teams or Slack webhook would reach whoever owns the data.
  • Pin dependency versions. The requirements give lower bounds only, so the build picked up a new major version of pandas on its first install. It worked, but that should be a decision, not an accident.
