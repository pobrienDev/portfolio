Turning an HR form into one reviewed command for onboarding and offboarding

At a multi-property organization, every hire meant a manual walk through the Entra admin center, and every departure meant a checklist that could be missed. I built a Python CLI that does the Microsoft Graph side of both in a single command, with a dry run for everything, lockout before cleanup, and an audit line for every write.

The problem

A hire arrives as a form submission attached to a help-desk ticket: name, title, property, start date, which platforms they need. Turning that into a working account was a sequence of portal screens, each with a chance to mistype a name, pick the wrong license, or forget a group. Some hires take over an existing role account rather than getting a new one, which added a second, different sequence. Offboarding was worse, because a missed step there is not a support ticket, it is a former employee with a working login.

The tool collapses each sequence into one command driven by a small YAML file built from the form. It creates or reuses the account, assigns the license, joins the right groups, and drafts the credential email; on departure it disables the account and revokes every session first, then strips groups and licenses. Anything Graph's application model cannot or should not do is printed as a ready-to-paste step rather than silently skipped.

Decisions worth defending

App-only authentication at the core, operator sign-in only where it has to be. The tool authenticates as an app registration with client credentials, so it can only ever touch the tenant it is configured for, and every write command prints that tenant's ID and domain before doing anything. The exceptions are deliberate and opt-in: Exchange distribution lists, shared-mailbox conversion and drafts in the operator's own mailbox run as the signed-in operator behind explicit flags, borrowing the operator's rights for that moment instead of enlarging the app's.

Scoped permissions means reading the reference, not taking the first one that works. The app registration is documented with three application permissions for its core job, and each was chosen against Microsoft's Graph reference. GroupMember.ReadWrite.All rather than Group.ReadWrite.All, because the tool adds and removes members and never needs to create, delete or reconfigure a group. User.RevokeSessions.All because it is the only application permission the reference lists for session revocation. Password-profile writes and sign-in activity reads are added only if a feature needs them, and the tenant-wide application form of a permission is never taken where a delegated one does the job. The sandbox registration in my infrastructure case study is managed by Terraform with its own, broader permission list that has not yet been brought in line with this one.

Lockout first. Offboarding disables the account and revokes every session before any cleanup, and the tests pin that order. If anything fails later in the run, the person is already out. Related: a failed shared-mailbox conversion leaves the licenses in place, because unlicensing an unconverted mailbox starts its deletion clock.

Reuse or create is a human decision. The discover command reports a role account's status, whose name is on it, whether it is enabled, when it last signed in. The operator chooses reuse or new; the tool does the clicking either way. It also refuses the obvious mistakes: creating a second account for a name created in the last seven days, reusing an account that is still enabled, unless the operator overrides explicitly; and it never stacks a license on top of one outside the hire's chain, reporting it for the admin center instead.

Nothing sensitive in the repo, and no passwords in the log. The .gitignore was the first commit. Credentials live in a gitignored .env, tenant-specific IDs (groups, SKUs) in a gitignored config, per-hire files are never committed, and the audit log records actions taken, never passwords or contact details. The README also says plainly where that stops: the audit log is a local file the operator could edit, so for an authoritative record, Entra's own audit log is the source, and every directory change the tool makes appears there under the app's identity.

What a run looks like

Without --yes, reuse and terminate only preview; with --dry-run any write command previews, even alongside --yes, and touches neither the tenant, the clipboard nor Outlook. A run exits non-zero when work remains for a human, such as a distribution list removal that has to happen in Exchange, or a directory role the account holds, so a script calling it cannot mistake "printed a follow-up" for "done".

Testing against a tenant you must never touch

The suite started at eight tests. The first expansion added a fake Graph client that records every call in order, which is what lets the tests assert things like "disable before revoke before cleanup" rather than just "it returned". Every test that drives a command replaces the Graph client, the config and the log directory, and the .env loader is stubbed or pointed at a temporary file, so nothing in the suite can read a real .env or reach a real tenant. CI runs it on two Python versions on every push.

Before trusting the suite I checked that it could fail: seven deliberate mutations in a scratch copy, such as skipping session revocation or letting dry-run write, and each one turned a test red. A test that has never been seen to fail is not evidence of much.

Two bugs worth telling

An apostrophe that could run commands in Exchange

The opt-in distribution-list step generates a PowerShell script for an Exchange Online session. It built single-quoted strings from each list's address without doubling apostrophes. An apostrophe is legal in an email address, so a list like o'brien-team@example.com produced a script that failed to parse, and a hostile address could have closed the string and run whatever followed inside an admin session. The fix applied the same doubling rule the script already used for the account name and path; the later audit folded all of it into one ps_quote helper that also covers typographic quotes. Two apostrophe tests were written first and failed against the old code before the fix made them pass; a third pins that a hostile address stays data.

Forty-eight audit findings, and the ones I said no to

Two months in, I ran a full audit of the tool and worked through all forty-eight findings in one pull request, re-checking each against the current code first. The test count went from 53 to 241. Some findings changed behaviour that a user would notice: reuse now requires --yes like terminate; the .env next to the script wins over variables left in the shell; the delegated token cache moved out of the repository folder into an owner-only file under the user's profile; a create is no longer retried after a gateway timeout, because the first attempt may have succeeded.

Some findings I deliberately did not fix, and the pull request says so: moving to a certificate credential is an architecture change, so the README documents the secret's blast radius and handling instead; the initial password still reaches the clipboard, and the banner now says so rather than pretending otherwise. The audit also produced a permission table for the production app registration, with the reasoning from the Graph reference for each entry, showing which permissions to add, which to replace with a narrower one, and why.

Outcomes

  • Onboarding and offboarding each run as one reviewed command instead of a portal walkthrough, with the same steps every time.
  • The departure path cannot leave a working login behind by accident: lockout is the first action, and the follow-ups it tracks, distribution-list removals and directory roles, fail the run until they are done.
  • 246 offline tests on two Python versions, green on every push to main, and a suite that has been shown to catch the mistakes it exists to catch.
  • Two sibling projects grew out of it: a published CLI that flags stale accounts, and the Terraform that provisions the identity the tool runs as.

What I would do differently next

  • A certificate or managed identity instead of a client secret, which removes the secret's blast radius rather than documenting it.
  • A Temporary Access Pass instead of an initial password on the clipboard, so no reusable credential ever passes through the operator's machine.
  • Pull the form fields from the help-desk ticket automatically. It is designed for and blocked on inconsistent submissions, which is a process fix before it is a code fix.
  • A fully pinned, hash-checked dependency set for the CI environment.
